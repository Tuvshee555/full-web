# Lorentz chatbot audit and gap analysis (1 November 2026)

Target: this repository (`src/chatbot/`, the Lorentz shop assistant). Reference: the Uudam Travel
chatbot at `C:\Dev\uudam-company\Uudam-Chatbot`, read only: no file, setting, deployment or
credential of Uudam was touched, and nothing travel-specific or customer-specific was copied.

## 1. What was found in Lorentz before the work

The assistant was already a port of the Uudam engine (one `runCustomerTurn` behind a lease/dedup
handler, deterministic answers first, a verified AI writer second, hand-offs that never silence the
bot). It worked for single questions but the live data and a 147-conversation evaluation showed
where it fell short.

| Area | Finding (before) |
| --- | --- |
| Product knowledge | `PRODUCT_CONTENT` in `src/config/store-data.mjs` was empty, and the `Product` table had no usage, ingredient, volume or FAQ fields. "How do I use it?" answered "see the product page", where there was nothing either. The owner had no way to publish these facts without a code change. |
| Purchase intent | "Нэгийг авъя" / "serum avya" / "odo hudaldaj away" had no path. A live customer who wrote "odo hudaldaj away" (I'll buy it now) was asked for an order number and phone, because the model read it as an order-status question. |
| Checkout help | The bot could only point at the cart and checkout pages; nothing put the product in the cart or created an order. |
| Latin-script Mongolian | A short alias list (`une`, `hed`, `bgaa`, …) covered common words; `hurgej ugh uu`, `yarih hun bna uu`, `hezee ur dun garah ve`, `tos odo belen bn uu` fell through to the generic "I am the assistant" line. |
| Product matching | The function word "Харин" (however) fuzzy-matched the pencil "Нарийн", so "Харин яаж хэрэглэх юм?" after a serum question answered about the pencil. "хар хүрэн" resolved to the shorter shade "Хүрэн". An unknown name sharing one word with the catalogue could be "verified" as a product. |
| Volume, frequency, duration | No "хэдэн мл" topic; frequency/duration questions got the generic usage line. |
| Shop FAQ | Only the three fixed policy FAQ entries in code; the owner could add free text in "extra knowledge" but the bot quoted it only when the model chose to. |
| Hand-over | `needsHuman` + one lead + a Telegram alert worked, but with no reason, no customer name or phone on the conversation list, no notes, no search, and a taken-over chat stayed with the owner forever. |
| Analytics | Totals only (conversations, leads). No purchase intent, no checkout clicks, no unanswered questions, no model usage or cost. |
| AI cost | Two gpt-4.1 calls per model turn, no ledger, no budget; an exhausted balance would only show in the error log. |
| Admin | Settings, Test chat, Activity, Log. No knowledge management, no per-product fact completeness. |

Live data (read only): 3 real conversations, 11 messages, no leads, no errors. The real messages were
all Latin script ("tanai buteegdhuni une hedwe", "odo hudaldaj away").

## 2. Uudam patterns reused (engineering, not travel content)

| Uudam pattern | Lorentz use |
| --- | --- |
| Durable lead before any staff alert (`durableLead.ts`) | Kept; the lead now carries a reason and the conversation context (`leadContext.ts` idea). |
| Takeover check again right before sending (`takeoverGuard.ts`) | Kept (handler rechecks `paused` after the model wait). |
| Hand-back marker (`bot_released_at`) so old staff replies cannot re-pause | `botReleasedAt`, plus automatic hand-back after the owner's silence limit (`shouldAutoResume`). |
| Daily model ledger per environment/model/source with an estimated cost and a daily budget (`aiUsage.ts`) | `ChatAiUsage` + `aiUsage.ts`; over budget the assistant answers from rules only. |
| Spend guard for evaluation runs (`evalGuard.mjs`) | `scripts/lib/evalGuard.mjs`: opt-in, capped, never production. |
| Conversation-level regression gate in CI (`qa:conversations`) | `tests/chatbot/eval-suite.test.ts` runs the 147-conversation set in `npm test`. |
| Latin number words read deterministically | A full Latin→Cyrillic alias layer in `textNorm.ts`, applied to every intent pattern. |
| Lead attention tiers | Simplified: hand-off reason pills and "waiting since" in the inbox. |
| Prompt-injection posture: system channel + "data, never instructions" | Kept; plus the deterministic layers never read model output as facts. |

Not reused: trips, departures, posters, Google Drive sync, the flow builder, Redis, Uudam's QPay path,
customer conversations, prompts about travel, and any Uudam credential.

| Capability | Uudam | Lorentz before | Lorentz now |
| --- | --- | --- | --- |

## 4. Measured results and how far to trust them

### What the numbers count

- **147** is the number of test conversations in the main set (`tests/chatbot/eval/cases.mjs`);
  **208** is the number of customer turns inside them. Both before and after runs use the same
  147 conversations; none was removed.
- A turn is correct when it passes the hard rules (a non-empty reply, no amount that is not a
  catalogue amount or a correctly computed total, the customer's language, no private order data,
  no growth promise, and an order only on the confirmation turn) and every expectation written for
  it (regular expressions the reply must or must not contain, hand-off or not).
- The catalogue is invented (`fixture.mjs`) and held in memory. The "sync" cases change it between
  turns the way an admin edit would; that proves the engine reads the catalogue on every turn, not
  that the database read works. The database path is tested separately by `npm run
  test:chatbot:db` (11 checks on a temporary PostgreSQL, including an edit through the real product
  controller that shows up in the next answer).

### Why 208/208 is not a measure of real quality

- The same person wrote the cases and the engine, and the engine was fixed until every case passed.
  Some alias words in `textNorm.ts` come straight from case wording.
- The purchase and chat-order expectations look for things only the new code produces (the
  `/buy/` link, the confirmation summary), so the old engine fails them by construction. Those
  categories measure that the feature exists.
- Coverage is uneven: only 32 of 208 turns are Latin-script Mongolian, although every real customer
  message in the live database is written in Latin letters; 55 turns repeat another turn's text;
  9 turns check only the hard rules.
- One methodology flaw was fixed during this review: computed order totals were accepted as true
  amounts on any line of any reply. They are now accepted only on lines that present a total or a
  multiplication. Scores did not change.

### Corrected scores (no model, same harness for both engines)

| Set | Before (engine on `main`) | After (this branch) | Hard rules after |
| --- | --- | --- | --- |
| Main set, categories that existed before (162 turns) | 138 (85.2%) | 162 (100%) | all |
| Main set, purchase and chat-order categories (46 turns) | 19 (41.3%) | 46 (100%) | all |
| Main set, all 208 turns | 157 (75.5%) | 208 (100%) | 208/208 |
| **Held-out set, 59 turns** | **32 (54.2%)** | **45 (76.3%)** | **59/59** |

The held-out set (`tests/chatbot/eval/heldout.mjs`, 51 conversations) was written after the engine
was frozen, mostly in Latin script and casual typing, and was run once; the engine was not changed
to pass it. It is the more honest number: the rules-only layers answer about three in four turns
on unseen phrasing, never invent a fact and never go silent. Its misses are Latin spellings the
alias table does not know ("udurtuu", "nairlagiig", "hedeer", "bnu", "evdersen"). In production the
model handles many of these, but a held-out run with the model has not been done yet.

The before-engine was scored on the same fixture, which includes usage steps and ingredients. In
the live shop before this work those facts did not exist anywhere, so the real "before" was lower
on usage, ingredient and volume questions than this table shows.

### With the model (subset of 62 conversations, 74 turns)

Before: gpt-4.1 50/74 (67.6%). After: gpt-4.1 71/74 (95.9%). Details and other models in
`MODEL_EVAL.md`. A test conversation is not a customer conversation: these numbers say the engine
behaves as designed on these phrasings, not that real customers will get the same rate.

## 5. Owner decisions still open

- Fill the product facts (volume, how to use, ingredient list, safety note, FAQ) for each product in
  Admin → Products; until then the assistant says the fact is not published and offers the team's contact.
- Keep chat orders on (default) or switch them off in Admin → Chat assistant → Settings.
- The daily AI budget (default $5) and the model (default: the server's `OPENAI_MODEL`).
- Delivery, returns and safety wording stays in `src/config/store-data.mjs` because the Terms page
  must say exactly the same; changing it is a code change.
